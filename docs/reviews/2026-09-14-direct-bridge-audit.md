# Prepared pipeline → direct OpenAPI: independent audit

Date: 14 September 2026. Scope: source inspection only; no credentials, external writes or main database changes. This records the pre-bridge baseline while other agents implement isolated transport/codec/journal modules. It is not acceptance of that later implementation.

## Decision

Keep the prepared application in `simulation`/`unavailable`. A signed HTTP client alone cannot safely replace `PreparedGateway`: the current gateway represents a whole listing mutation, whereas Shopee requires several independently acknowledged calls. The safe next increment is an isolated sandbox transport, pure request/metadata codecs and a persistent step journal, followed by integration with explicit source context and readback. Production remains read-only.

## Useful existing mechanisms

- `apps/worker/src/sandbox-create-trials.ts` separates `queued → create_intent → created → tiers_intent → readback`; `beginMutation` persists before each network call. A storage error intentionally leaves an unresolved intent. This is a suitable pattern for the new journal.
- `packages/shopee/src/field-client.ts` rejects partial/malformed success partitions, treats transport/server ambiguity as unknown, uses a fixed sandbox host and redacts echoed secrets. The older product client should not be copied without those error-classification checks.
- Prepared coordinator already has connection/capability revision checks, per-owner lane locks, explicit selected fields/SKUs, fresh update baseline checks, reservations, and read-only unknown recovery. Keep these invariants across the bridge.
- Gallery updates must preserve the separately selected cover via `promotion_images`; a verified gallery write alone does not prove cover preservation. The prior Lamy unknown run demonstrates this risk.

## Recommended bounded sequence

1. Parse complete raw metadata responses and preserve evidence/date/scope. No sample-number fallback and no fabricated `maxModels` from `get_item_limit`.
2. Compile a source-complete document into immutable OpenAPI steps before uploading or creating anything. Include exact item/model targets, field mask and expected readback facts. Validate every later step up front.
3. Resolve cached media; journal each missing upload. Use explicit scene/ratio and keep bytes unchanged.
4. For create, persist `add_item` UNLIST dispatch, record returned item ID, read it, then initialize exact tiers/models and bind returned model IDs by SKU + tier index. An incomplete link remains incomplete; do not publish or create a duplicate.
5. For update, read a fresh target baseline and promotion/location state, then dispatch only selected endpoint steps/chunks. Preserve independent gallery, description and variation-image ordering. Read and compare each step, retaining partial success evidence.
6. Recheck connection scope/revision immediately before every write. A token refresh is a credential transition, never authority to replay an unknown mutation. All other executors must respect the same shop/item lock.
7. Exercise signed local HTTP fixtures, multi-step crash/restart, partial API success, 401/429/5xx, stale metadata, changed source, promotion lock and image-ID rewrite. Then perform a separately authorized bounded sandbox trial with exact scope. Main prepared UI and production write mode remain closed until this integration is accepted.

## Follow-up review of the isolated wire increment

Reviewed `apps/api/src/prepared-wire-runner.ts`, `packages/shopee/src/prepared-transport.ts`, migration 014 and the corresponding unit/integration test sources on 14 September. This follow-up is independent source review; it does not claim to have rerun another agent's database or transport suite.

Three P1 findings were sent to the owner and the resulting code changes were re-read:

1. **Credential revision could defeat create deduplication.** The first implementation included connection/capability revisions in its logical fingerprint and had no stable create reservation. The revised fingerprint excludes those revisions and preparation now checks an existing create operation for the same owner/source key, regardless of a changed source hash or new operation ID. Same-ID changed-intent requests still fail. This fixes the identified duplicate path within this runner; binding and lock coordination with legacy executors remains an integration gate.
2. **Connection could change between credential lookup and recorded dispatch.** The runner now rechecks environment, partner/shop, connection/capability revision, state and expiry with `FOR SHARE` in the transaction that records the sent step. This establishes the durable dispatch boundary against a prior stale context read. The runner still never reuses refreshed credentials to replay an unknown step.
3. **Transport discarded partial error receipts.** Outcomes now retain a recursively redacted full envelope and classify server/network ambiguity as unknown. Acknowledgement inspection consumes that envelope rather than reconstructing one with an invented empty error. Failed or partial outcomes remain unknown in the journal and cannot automatically advance or resend. This permits later inspection of exact API success/failure partitions without calling them readback verification.

The source review also confirms: fixed sandbox host and explicit owner allowlist; no redirects; separate public upload signing; protected Lamy/sample IDs blocked; create requires UNLIST; update plans cannot mix item IDs; journal intent is committed before network dispatch; a lease-expired sent stage is quarantined; only an acknowledged prior stage permits an unsent subsequent stage; terminal unknown/acknowledged journal rows cannot be reset by the application. The operation's final success label is deliberately `acknowledged`, never `verified`.

Remaining integration limits are material. The prepared main gateway and worker are not switched to this bridge. No automatic unknown reconciliation or per-field QC is integrated into the wire runner. Its create reservation is local to this journal rather than a shared binding with the existing trial/Lamy executors. A previously blocked, unsent operation may require an explicit new preflight/recovery design; deduplication is not a generic retry mechanism. Metadata assessment covers a complete create source; do not require unrelated condition/preorder/GTIN fields for a title-only update that preserves its fresh baseline.

### Read-only sandbox probe and parser correction

Reviewed the owner's saved probe at `.local/acceptance-20260914/wire-bridge/2026-09-14T05-56-40.201Z/readonly-probe.json` (six API reads, zero mutations; sandbox shop 227418363, category 301378). These observations are specific to that shop/category/time:

- `size_chart_mandatory` is **omitted**, even though both size-chart support flags are false. Neither flag proves that a size chart is optional. The codec blocks create; the metadata assessor now reports the same unknown requirement. The raw probe was not modified to supply false.
- Several single combo-box attributes omit `max_value_count`. A single value is established by the returned SINGLE input-type enum itself; it is not an API-example fallback. The assessor now accepts that defined cardinality while still requiring an actual maximum for multi-select attributes.
- SPF Mart 50040 reports zero volume limits and zero dimension sum. This review does not interpret zero as unlimited. The codec/transport must retain the unresolved restriction and not switch channels or amend package dimensions to pass.
- The logistics request ID contains colon-separated components. The transport accepts this observed shape and keeps the exact redacted identifier.

The new pure assessor is `packages/shopee/src/prepared-metadata.ts`; tests are `tests/unit/prepared-metadata.test.ts`. **15/15** tests passed in this agent's own run, including the two probe-derived regressions (observed failing before their fix). Evidence: `.local/prepared-verification/prepared-metadata-unit-results.json`. These tests use raw response fixtures and make no Shopee calls. The assessor neither fabricates a model-count limit nor changes source text, media, price, stock, GTIN or brand to achieve compatibility.

For the separately proposed title-only canary update, the bounded review requirement is: freshly verify the existing technical trial binding and shop/item/prefix, record the complete before snapshot, send only the intended title once through the journal, then compare that title and every preserved business field from an independent read. A missing or mismatched readback stays unknown. This is a review condition, not evidence that the canary has executed.
